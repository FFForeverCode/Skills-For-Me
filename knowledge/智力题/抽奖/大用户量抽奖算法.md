## 公司有1个亿的用户,用户表:user_id,name,联系方式,请你设计抽奖工程实践和一个随机抽奖算法,随机抽取一个幸运用户

如果让我在面试中给出一个**最终可落地方案**，我会选择：

# 1. 最终方案：用户快照 + 连续 Slot + 无偏随机抽样

核心思想：

> **提前生成有效用户快照，为每个用户分配连续 `slot_id`，抽奖时只随机生成一个 `slot_id`，再映射到 `user_id`。**

整体架构：

```text
                         ┌──────────────┐
                         │   用户 MySQL  │
                         └──────┬───────┘
                                │
                         定时生成快照
                                ↓
                    ┌─────────────────────┐
                    │ Lottery User Snapshot│
                    │ slot_id → user_id   │
                    └──────────┬──────────┘
                               │
                         快照版本冻结
                               ↓
                      ┌────────────────┐
                      │ Lottery Service│
                      └───────┬────────┘
                              │
                       生成安全随机数
                              ↓
                     Random Index [0,N)
                              ↓
                       slot_id → user_id
                              ↓
                       ┌─────────────┐
                       │中奖用户结果 │
                       └──────┬──────┘
                              ↓
                     MySQL 持久化结果
```

# 2. 第一步：生成抽奖用户快照

假设当前有：

```text
1亿注册用户
```

但是并不是所有用户都有资格参加抽奖，所以先根据业务规则筛选：

```sql
SELECT user_id
FROM user
WHERE status = 1
  AND lottery_eligible = 1;
```

假设最终得到：

```text
N = 80,000,000
```

然后建立：

```text
slot_id    user_id
0          10001
1          10008
2          10013
3          10021
...
79999999   987654321
```

注意：

> **slot_id 必须连续，不能直接使用 user_id 作为随机范围。**

因为 `user_id` 可能存在删除、注册空洞等情况。

---

# 3. 为什么要做快照？

因为抽奖过程中用户集合必须保持不变。

例如：

```text
10:00  抽奖开始
10:01  用户A注销
10:02  用户B注册
10:03  抽奖
```

如果实时查询用户表，那么参与抽奖的用户集合可能发生变化。

所以抽奖开始前：

```text
Snapshot V20260819001
```

一旦生成：

> **整个抽奖过程只使用这个 Snapshot。**

这样抽奖规则是确定的。

---

# 4. 第二步：生成随机下标

假设：

```text
N = 80,000,000
```

生成：

```text
index ∈ [0, 79,999,999]
```

使用：

```java
SecureRandom random = new SecureRandom();

int index = random.nextInt(userCount);
```

然后：

```text
userId = snapshot[index]
```

例如：

```text
random index = 738291
```

那么：

```text
snapshot[738291]
        ↓
user_id = 12345678
        ↓
中奖用户
```

---

# 5. 为什么这个算法公平？

假设共有 `N` 个用户。

`nextInt(N)` 保证：

[
P(index=i)=\frac{1}{N}
]

而：

```text
slot_id ↔ user_id
```

是一一映射。

所以：

[
P(user_i中奖)=\frac{1}{N}
]

例如 8000 万用户：

[
P(user_i中奖)=\frac{1}{80,000,000}
]

每个用户概率完全相同。

---

# 6. 防止随机数模偏差

如果自己实现随机算法，不能简单：

```java
index = randomLong % N;
```

因为可能产生 **Modulo Bias**。

所以如果自己实现，我会采用**拒绝采样**：

```text
生成随机数 R

        ↓

R 是否落在
完整的 N 倍区间？

   ↓是             ↓否
 R % N          丢弃重新生成
   ↓
 index
```

这样才能保证严格等概率。

不过 Java 中直接使用：

```java
SecureRandom.nextInt(N)
```

即可，不需要自己重新实现。

# 7. 第三步：防止分布式重复抽奖

假设 Lottery Service 有 20 台机器：

```text
          Gateway
             │
     ┌───────┼───────┐
     ↓       ↓       ↓
    S1      S2      S3 ...
```

不能让多个节点同时产生不同结果。

我会设计：

```text
lottery_id
```

作为唯一抽奖 ID。

数据库：

```sql
CREATE TABLE lottery_result (
    lottery_id       BIGINT PRIMARY KEY,
    snapshot_version VARCHAR(64),
    random_index     BIGINT,
    user_id          BIGINT,
    random_seed      VARCHAR(128),
    create_time      DATETIME
);
```

`lottery_id` 是主键。

多个节点同时抽奖：

```text
S1 ─┐
S2 ─┤
S3 ─┤──→ INSERT lottery_result
... │
S20┘
```

最终只有一个节点能够成功插入。

所以：

> **Redis 分布式锁负责降低并发竞争，MySQL 唯一索引负责最终一致性兜底。**

还应该记录：

```text
random_index
```

验证最终中奖结果。

# 9. 1亿用户如何存储？

我不会直接：

```java
List<User>
```

因为 Java 对象开销很大。

只需要保存：

```text
slot_id → user_id
```

即可。

`user_id` 如果是 `long`：

```text
1亿 × 8 Bytes
≈ 800 MB
```

可以进一步做：

```text
Snapshot
├── shard-00
├── shard-01
├── ...
└── shard-99
```

每个 shard 100 万用户。

随机得到：

```text
index = 73,829,291
```

计算：

```text
shard = 73
offset = 829291
```

只读取：

```text
shard-73
```

然后：

```text
user_id = shard-73[offset]
```

所以**抽奖本身仍然是 O(1)**。

# 11. 最终面试版

如果面试官让我**最终设计一个 1 亿用户随机抽 1 人的系统**，我会这样回答：

> **我会采用“用户快照 + 连续 Slot + 安全随机数”的方案。**
>
> 首先根据抽奖规则从 1 亿用户中筛选出符合条件的用户，生成一个冻结的 Snapshot，并给每个用户分配连续的 `slot_id`，建立 `slot_id → user_id` 的映射。抽奖开始后不再修改这个 Snapshot。
>
> 抽奖时获取有效用户数 `N`，使用 `SecureRandom.nextInt(N)` 生成 `[0,N)` 范围内的随机下标，再通过 Snapshot 根据下标 O(1) 找到对应用户。由于每个 slot 被选中的概率都是 `1/N`，并且 slot 和用户是一一映射的，因此可以保证每个用户等概率中奖。
>
> 分布式部署下，我会使用 `lottery_id` 做唯一标识，通过 Redis 锁控制并发，同时在 MySQL 的抽奖结果表上建立 `lottery_id` 唯一索引作为最终幂等保障。最终记录 Snapshot 版本、随机种子、随机下标、中奖用户和算法版本，保证抽奖结果可以审计和复现。
>
> **整个抽奖过程的核心复杂度是 O(1)，不需要在抽奖时扫描 1 亿用户。**

这个方案我认为最适合面试，因为它同时回答了 **随机算法、公平性、1亿数据量、并发、幂等、可审计** 六个问题。

# 六、一个关键问题：用户在抽奖过程中注册怎么办？

因为你说的是：

> **1 亿个用户全部自动参与。**

那么必须明确一个规则：

### 方案 A：活动开始时的 1 亿用户参加

例如：

```text
2026-08-19 00:00
```

冻结用户集合。

那么：

```text
00:00之前的用户 → 参加
00:00之后注册 → 不参加
```

这是我最推荐的。

这样抽奖池：

```text
Snapshot V1
```

一旦生成就不会变化。

---

### 方案 B：活动期间注册的用户也自动参与

那就不能简单冻结 1 亿用户。

例如：

```text
00:00 → 100,000,000 用户
12:00 → 100,100,000 用户
```

这时候需要定义：

> **到底以哪个时间点的用户数量作为抽奖基数？**

否则概率会发生变化。

所以正式活动一般都会规定：

> **活动开始时的全量用户作为抽奖池，之后新增用户不参与本次抽奖。**

这样规则最清晰，也最容易审计。

# 1亿个用户存到一张表中吗?如何优化?

可以存**一个逻辑用户表**，但物理上不建议把“1 亿用户 + 抽奖数据 + 其他业务字段”全部堆在一张超宽表里。

不过这里要区分两个问题：

> **用户主数据怎么存？**
> **抽奖时怎么高效随机定位 1 亿用户？**

我会这样设计。

## 1. 用户表：逻辑一张，物理分库分表

如果是 1 亿用户，MySQL 完全可以存，但生产环境一般会考虑分库分表：

```text
                    User Service
                        │
                user_id 路由
                        │
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
     DB-00           DB-01           DB-02 ...
      ↓                ↓                ↓
   user_000         user_001         user_002
```

例如：

```text
16 个库 × 16 张表
```

总共：

```text
256 张 user 表
```

按照 `user_id` 做 Hash：

```text
dbIndex  = hash(user_id) % 16
tableIndex = hash(user_id) % 16
```

这样单表大约：

[
1亿 / 256 \approx 39万
]

单表压力会小很多。

# 2. 但是抽奖千万不要每次去查 MySQL

这是这道题最关键的地方。

如果抽奖：

```text
random = 738291
       ↓
SELECT ...
FROM user_xxx
WHERE ...
```

你首先还要解决：

> `738291` 怎么映射到具体的 user_id？

而且如果直接在 1 亿用户表上做：

```sql
ORDER BY RAND()
LIMIT 1;
```

**绝对不能这么干。**

因为 `ORDER BY RAND()` 会产生大量随机数并进行排序，1 亿数据量下成本非常高。

我会把**业务用户表**和**抽奖池**彻底解耦。

```text

├── ...
└── user_255
```

```text
Lottery Snapshot

```

这样抽奖系统完全不需要关心用户表怎么分库分表。

# 4. Snapshot 甚至不需要 MySQL

因为我们的需求只有：

```text
slot_id → user_id
```

没有复杂查询。

所以我更倾向于：

```text

       ↓

       ↓
   Snapshot File
       ↓

       ↓

```

例如生成一个二进制文件：

```text
snapshot-v1.bin
```

里面连续存储：

```text
long userId[100000000]
```

一个 `long` 8 字节：

[
1亿 × 8B = 800MB
]

也就是说：

> **1 亿用户的抽奖索引只需要大约 800MB。**

而不是把整个：

```text
user_id
name
phone
email
address
...
```

全部加载进内存。

# 5. 更进一步：分片 Snapshot

800MB 对单机内存来说其实也不算特别大，但我不会让一个实例承担全部数据。

可以拆成：

```text
snapshot/
├── shard-000
├── shard-001
├── ...
└── shard-099
```

每个 shard：

```text
1,000,000 users
```

大小：

[
1,000,000 × 8B = 8MB
]

抽奖得到：

```text
index = 73,829,291
```

计算：

```text
shard = index / 1,000,000
      = 73

offset = index % 1,000,000
       = 829,291
```

于是：

```text
snapshot-073[offset]
```

直接得到：

```text
user_id
```

整个过程：

```text
O(1)
```

# 6. 为什么不直接把 1 亿 user_id 放 Redis？

可以，但我**不推荐把 Redis 当长期抽奖池**。

例如：

```text
Redis List
1亿 user_id
```

虽然 Redis 可以扛，但：

* 占用大量内存
* 数据持久化成本增加
* 这个数据一年可能只用一次
* Redis 本身更适合高频访问数据
* 没必要为了一个随机抽奖消耗大量 Redis 内存

这种场景：

> **Snapshot 文件 + 本地缓存 / mmap，比 Redis 更合适。**

# 7. 如果用户表已经分库分表，怎么生成 Snapshot？

可以做一个离线任务：

```text
                256张用户表
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    DB Task       DB Task      DB Task
       │            │            │
       └────────────┼────────────┘
                    ↓
              Merge / Sort
                    ↓
             Snapshot V1
```

因为 1 亿数据量并不适合单机 Java：

```java
List<Long> users = new ArrayList<>(100_000_000);
```

直接这么搞内存压力很大。

可以采用：

> **分页/游标读取 + 流式写入 Snapshot。**

例如每个分片：

```sql
SELECT user_id
FROM user_xxx
WHERE user_id > ?
ORDER BY user_id
LIMIT 10000;
```

然后持续生成：

```text
snapshot-000
snapshot-001
...
```

---

# 8. 还有一个很重要的优化：不要存 `name、联系方式`

你的原始用户表：

```text
user_id
name
联系方式
```

抽奖其实只需要：

```text
user_id
```

所以：

```text
Lottery Snapshot
```

只保存：

```text
slot_id → user_id
```

中奖之后再：

```text
winner_user_id
      ↓
User Service
      ↓
查询 name / 联系方式
      ↓
发送通知
```

也就是：

> **冷热数据分离。**

抽奖池是热数据：

```text
slot → user_id
```

用户详情是冷数据：

```text
user_id → name / contact
```

# 9. 最终架构

我会最终设计成：

```text
                    用户中心
                       │
                1亿用户数据
                       │
             MySQL 分库分表
                       │
                       │ 离线生成
                       ↓
              ┌─────────────────┐
              │ Lottery Snapshot│
              │ 只保存 user_id  │
              └────────┬────────┘
                       │
                 分片二进制文件
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
     Shard 0        Shard 1        Shard 99
       8MB             8MB             8MB
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                Lottery Service
                       │
                SecureRandom
                       │
                  random index
                       │
                       ↓
               shard + offset
                       │
                       ↓
                  user_id
                       │
                       ↓
                 User Service
                       │
                 用户详细信息
                       │
                       ↓
                    MQ
                 /   |   \
              短信 Push 站内信
```

### 面试一句话

> **1 亿用户的业务数据可以采用 MySQL 分库分表存储，但抽奖不直接操作用户表。我会在活动开始前通过离线任务生成用户 Snapshot，只保存连续索引到 `user_id` 的映射，并按 100 万用户一个分片存储。抽奖时生成一个随机 index，通过 `shard = index / 100万`、`offset = index % 100万` O(1) 定位用户。中奖后再根据 user_id 查询用户详情。这样把“1 亿用户的存储问题”和“随机抽奖问题”解耦，同时避免 `ORDER BY RAND()`、全表扫描和 Redis 存储 1 亿用户带来的成本。**
