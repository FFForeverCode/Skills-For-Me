描述：用于诊断疑难缺陷和性能退化问题的诊断循环。当用户说“诊断”/“调试此问题”或报告出现故障/抛出异常/失败/运行缓慢等情况时使用。

# 诊断缺陷

一种用于诊断疑难缺陷的方法。仅在明确需要时才跳过某些阶段。

诊断范围:
1. 代码库全量诊断:当用户**未指明确定代码文件、位置、git分支**且**明确指出进行全量诊断时**对整个代码库执行全量诊断.在探索代码库时，请阅读 `CONTEXT.md`（如果存在）以清晰了解相关模块，并检查您正在处理的区域的 ADR（应用定义规则）。
2. 指定分支诊断: 当用户指定确定的代码分支后,对当前分支与master主分支之间的新增代码及其文件进行缺陷诊断.

## 编辑

此技能要求您展示命令、输出和捕获的工件。**首先编辑所有敏感信息**——用 `<REDACTED>` 代替。针对环境变量构建循环，以便凭据保留在环境中，而不是出现在您展示的内容中。捕获的工件包含身份验证标头：仅引用包含信号的行。

如果经过编辑的输出不足以诊断错误，请说明情况并询问用户。

## 第一阶段 — 构建反馈循环

**这是关键技巧。** 其他一切都是机械操作。如果你有一个**明确的**通过/失败信号——一个针对_这个_错误的信号——你就能找到原因；二分法、假设检验和插桩都只是利用了这个信号。如果没有这样的信号，再多地盯着代码也无济于事。

在此投入大量精力。**积极主动。发挥创造力。永不放弃。**

### 构建反馈循环的方法 — 大致按以下顺序尝试

1. **在任何到达错误的测试节点上测试失败** — 单元测试、集成测试、端到端测试。

2. **使用 curl / HTTP 脚本** 测试正在运行的开发服务器。

3. **使用 fixture 输入调用 CLI**，并将标准输出与已知良好的快照进行比较。

4. **无头浏览器脚本**（Playwright/Puppeteer）——驱动用户界面，断言 DOM/控制台/网络。

5. **重放捕获的跟踪**——将真实的网络请求/有效负载/事件日志保存到磁盘；在隔离的代码路径中重放它。

6. **一次性测试框架**——启动一个最小的系统子集（一个服务，模拟依赖项），通过单个函数调用来执行错误代码路径。

7. **属性/模糊测试循环**——如果错误表现为“有时输出错误”，则运行 1000 个随机输入并查找故障模式。

8. **二分法测试框架**——如果错误出现在两个已知状态（提交、数据集、版本）之间，则自动化“从状态 X 启动，检查，重复”，以便可以使用 `git bisect run` 命令进行测试。

9. **差分循环**。使用相同的输入分别在旧版本和新版本（或两种配置）下运行，并比较不同的输出。

10. **HITL bash 脚本**。最后的手段。如果必须由人工点击，请使用 `scripts/hitl-loop.template.sh` 来引导他们，以确保循环结构完整。捕获的输出会反馈给您。

构建正确的反馈循环，即可解决 90% 的问题。

### 优化循环

将循环视为一个产品。一旦有了循环，就对其进行优化：

- 能否提高速度？（缓存设置、跳过无关的初始化、缩小测试范围。）

- 能否使信号更清晰？（断言具体的症状，而不是“没有崩溃”。）

- 能否使其更具确定性？ （锁定时间、设置随机数生成器种子、隔离文件系统、冻结网络。）

一个 30 秒的不稳定循环勉强比没有循环好一点；一个 2 秒的确定性循环则非常精准——这是调试的利器。

### 非确定性 bug

目标不是找到一个完美的复现步骤，而是提高**复现率**。将触发循环 100 次，并行化，增加压力，缩小时间窗口，注入睡眠。50% 的不稳定 bug 是可以调试的；1% 则不行——不断提高复现率，直到可以调试为止。

### 当你确实无法构建循环时

停止并明确说明。列出你尝试过的所有方法。请求用户：(a) 访问任何可以复现问题的环境，(b) 提供经过编辑的捕获工件（HAR 文件、日志转储、核心转储、带有时间戳的屏幕录像），或 (c) 允许添加临时生产环境插桩。**不要**在没有循环的情况下进行假设。

### 完成标准 — 紧密循环且出现红色错误

当循环**紧密**且**能够出现红色错误**时，第一阶段完成：您可以指定**一个命令**——脚本路径、测试调用或 curl 命令——该命令**至少运行过一次**（请提供调用及其输出，已编辑），具体如下：

- [ ] **能够出现红色错误** — 它能够驱动实际的错误代码路径并断言**用户的具体症状**，因此在发现此错误时会显示红色错误，并在修复后显示绿色错误。并非“运行无误”——它必须能够_捕获此特定错误_。

- [ ] **确定性** — 每次运行结果相同（不稳定错误：如上所述，具有固定且高复现率）。

- [ ] **快速** — 秒级，而非分钟级。

- [ ] **可由代理运行** — 您可以无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 脚本，人才能参与到循环中。

如果你发现自己在阅读代码并试图构建理论时，还没有这个命令，**请立即停止——直接跳到假设正是这项技能所要避免的错误。** 没有能够触发错误提示的命令，就没有第二阶段。

## 第二阶段 — 复现 + 最小化

运行循环。观察它是否变为红色——错误出现。

确认：

- [ ] 循环是否产生了**用户**描述的故障模式——而不是碰巧出现在附近的其他故障。错误的错误会导致错误的修复。

- [ ] 故障可以在多次运行中复现（或者，对于非确定性错误，复现频率足够高，以便进行调试）。

- [ ] 您已捕获到确切的症状（错误消息、错误输出、运行缓慢），以便后续阶段可以验证修复是否真正解决了问题。

### 最小化

一旦出现红色错误，将复现场景缩小到**仍然会触发红色错误的最小场景**。**逐一删除输入、调用者、配置、数据和步骤**，每次删除后重新运行循环——只保留导致故障的负载部分。

为什么要这样做：最小化复现步骤可以缩小第三阶段的假设空间（减少需要怀疑的因素），并在第五阶段成为干净的回归测试。

当**所有剩余元素都具有承载能力**时完成——移除任何一个元素都会导致循环结束。

在复现**并**最小化之前，请勿继续。

## 第三阶段 — 假设

在测试任何假设之前，生成**3-5 个排序合理的假设**。单假设生成以第一个看似合理的想法为基准。

每个假设都必须是**可证伪的**：陈述其预测结果。

> 格式：“如果 <X> 是原因，那么 <更改 Y> 将使错误消失 / <更改 Z> 将使错误恶化。”

如果您无法陈述预测结果，则该假设只是感觉——放弃或对其进行改进。

**在测试前向用户展示排名列表。** 他们通常具备领域知识，能够立即重新排序（例如，“我们刚刚部署了对第 3 项的更改”），或者知道他们已经排除的假设。这是一个成本低廉的检查点，却能节省大量时间。不要因此而停滞不前——即使用户不在，也继续进行排名。

## 阶段 4 — 检测

每个探针都必须映射到阶段 3 中的特定预测。**每次只更改一个变量。**

工具偏好：

1. 如果环境支持，则使用调试器/REPL 检查。一个断点胜过十条日志。

2. 在区分假设的边界处记录目标日志。

3. 切勿“记录所有内容并进行 grep 查询”。

**使用唯一的前缀标记每个调试日志，例如 `[DEBUG-a4f2]`。最后只需进行一次 grep 查询即可。未标记的日志保留；已标记的日志删除。

**性能分支。** 对于性能回归问题，日志通常是错误的。正确的做法是：先建立基准测量（计时工具、`performance.now()`、性能分析器、查询计划），然后进行二分查找。先测量，后修复。

## 第五阶段 — 修复 + 回归测试

**在修复之前**编写回归测试——但前提是存在**正确的接缝**。

正确的接缝是指测试能够重现调用点处**真实的 bug 模式**。如果唯一可用的接缝太浅（例如，bug 需要多个调用者时却只有单调用者测试，或者单元测试无法复现触发 bug 的调用链），那么在该位置进行回归测试会造成虚假的信心。

**如果不存在正确的接缝，那么这本身就是问题所在。** 记录下来。代码库架构阻碍了 bug 的锁定。标记此问题，以便在下一阶段处理。

如果存在正确的接缝：

1. 将最小化的复现示例转换为在该接缝处失败的测试。

2. 观察测试失败。

3. 应用修复方案。

4. 观察测试通过。

5. 针对原始（未最小化）场景重新运行第一阶段反馈循环。

## 第六阶段 — 清理 + 事后分析

完成以下事项前必须满足：

- [ ] 原始复现步骤不再可复现（重新运行第一阶段循环）

- [ ] 回归测试通过（或已记录无连接点）

- [ ] 所有 `[DEBUG-...]` 插桩已移除（使用 `grep` 命令搜索前缀）

- [ ] 已删除一次性原型（或已将其移动到明确标记的调试位置）

- [ ] 已在提交/PR 信息中说明最终被证实正确的假设——以便后续调试人员能够学习

**然后问自己：什么可以避免这个 bug？** 如果答案涉及架构变更（例如测试连接点不合理、调用者混乱、存在隐藏耦合），请将具体细节交给 `/improve-codebase-architecture` 技能团队。建议在修复完成后提出，而不是修复之前——现在您掌握的信息比开始时更多。
