--- 
名称：代码审查

描述：审查自指定固定点（提交、分支、标签或合并基点）以来的代码变更，审查维度包括两个方面：标准（代码是否符合本仓库的文档化编码标准？）和规范（代码是否符合原始问题/规范的要求？）。两个审查维度分别在多个子代理中并行运行，并将结果并排显示。适用于用户想要审查分支、PR、正在进行中的变更，或要求“审查自 X 点以来的代码”的情况。

---

对 `HEAD` 和用户指定的固定点之间的差异进行双轴审查：

- **标准** — 代码是否符合本仓库的文档化编码标准？

- **规范** — 代码是否忠实地实现了原始问题/规范？

两个维度作为**并行子代理**运行，因此不会相互干扰，然后该技能会汇总它们的审查结果。

问题跟踪器应该已经提供给您了——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户指定的固定点可以是提交 SHA、分支名称、标签、`main`、`HEAD~5` 等。如果用户没有指定，请询问。

捕获一次 diff 命令：`git diff <固定点>...HEAD`（三个点，表示比较的是合并基点）。同时，使用 `git log <固定点>..HEAD --oneline` 记录提交列表。

在继续操作之前，确认固定点已解析（`git rev-parse <固定点>`）且 diff 不为空。错误的引用或空的 diff 应该在此处失败——而不是在两个并行的子代理中失败。

### 2. 确定规范来源

按以下顺序查找原始规范：

1. 提交信息中的问题引用（例如 `#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。

2. 用户作为参数传递的路径。

3. `docs/`、`specs/` 或 `.scratch/` 目录下与分支名称或功能匹配的规范文件。

4. 如果未找到任何规范，则询问用户规范的位置。如果用户表示没有规范，则 **规范** 子代理将跳过并报告“没有可用的规范”。

### 3. 确定标准来源

仓库中任何记录代码编写方式的文件，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库文档中记录的内容之外，“标准”轴始终包含下方的**代码异味基线**——一组固定的 Fowler 代码异味（参见《重构》第三章），即使仓库没有任何文档也适用。它遵循两条规则：

- **仓库优先。** 已记录的仓库标准始终优先；如果仓库标准认可了基线会标记的内容，则抑制该异味。

- **始终需要判断。** 每个异味都是一个带标签的启发式规则（例如“可能存在特性偏好”），而不是一个硬性违规——并且，与此处的任何标准一样，忽略工具已经强制执行的任何内容。

每个异味的描述是：*它是什么* → *如何修复*；将其与差异进行比对：

- **名称不明**——函数、变量或类型，其名称无法揭示其功能或存储的内容。→ 重命名；如果找不到合适的名称，则说明设计存在缺陷。

- **重复代码** — 相同的逻辑结构出现在变更中的多个代码块或文件中。→ 提取共享的结构，并在两个代码块或文件中调用它。

- **功能偏好** — 某个方法访问了其他对象的数据，而不是自身的数据。→ 将该方法移到它所偏好的数据上。

- **数据聚集** — 相同的几个字段或参数不断一起出现（类似于想要创建新类型的情况）。→ 将它们打包成一个类型，然后传递该类型。

- **原始类型偏好** — 某个原始类型或字符串代表了一个应该拥有自己类型的领域概念。→ 为该概念赋予一个独立的类型。

- **重复的 switch 语句** — 相同的 switch/if 级联语句在变更中反复出现。→ 用多态性或两个站点共享的映射表替换它。

- **乱枪打鸟式修改** — 一个逻辑变更导致差异中的多个文件被分散修改。→ 将所有修改集中到一个模块中。

- **发散性变更** — 同一个文件或模块因多个不相关的原因而被修改。→ 将其拆分，使每个模块仅因一个原因而修改。

- **推测性通用性** — 为规范中不存在的需求而添加的抽象、参数或钩子。→ 删除它；将其内联，直到出现真正的需求为止。

- **消息链** — 调用者不应依赖的冗长的 `a.b().c().d()` 导航。→ 将其隐藏在第一个对象的某个方法之后。

- **中间人** — 主要只是进行委托的类或函数。→ 删除它，直接调用真正的目标。

- **拒绝继承** — 忽略或重写其继承的大部分内容的子类或实现者。→ 放弃继承，使用组合。
