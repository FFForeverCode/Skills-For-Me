# 改进代码库架构

发现架构摩擦并提出**深化改进的机会**——将浅层模块重构为深层模块。目标是提高可测试性和 AI 导航性。

此命令基于项目的领域模型，并采用共享的设计词汇表：

- 运行 `/codebase-design` 技能，获取架构词汇表（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆作用**、**局部性**）及其原则（删除测试、“接口即测试表面”、“一个适配器 = 假设的接缝，两个适配器 = 实际的接缝”）。在所有建议中务必使用这些术语——不要使用“组件”、“服务”、“API”或“边界”等词语。

- `CONTEXT.md` 中的领域语言为良好的衔接点命名；`docs/adr/` 中的 ADR 记录了此命令不应重新审查的决定。

## 流程

### 1. 探索

**扫描前先确定范围——YAGNI（You Aign I Need It，你不需要它）。** 深入理解一个模块有助于简化未来的修改，因此要格外关注代码库中最近发生过更改的部分。在查找之前，先确定查找*哪里*：

- 如果用户指明了一个方向——例如模块、子系统或痛点——则直接采纳，并跳过下面的推断。

- 否则，回溯一段较长的提交历史记录（`git log --oneline`），找到代码库的热点区域——反复出现的文件和区域——并首先关注这些路径。如果更改分散且没有明显的热点区域，则扩大搜索范围。

首先阅读项目的领域术语表（`CONTEXT.md`）以及你所接触领域的任何应用定义规则 (ADR)。

然后生成一个子代理来遍历代码库。不要遵循僵化的经验法则——要灵活探索，并记录遇到的阻力：

- 理解某个概念是否需要在多个小型模块之间来回切换？

- 哪些模块**浅层**——接口几乎与实现一样复杂？

- 哪些纯函数仅仅为了便于测试而被提取出来，但真正的 bug 却隐藏在它们的调用方式中（缺乏**局部性**）？

- 哪些紧密耦合的模块之间存在缺陷？

- 代码库中哪些部分未经测试，或者难以通过其当前接口进行测试？

对任何你怀疑是浅层的模块应用**删除测试**：删除它会集中复杂性，还是仅仅转移复杂性？“是，集中复杂性”就是你想要的信号。

### 2. 以 HTML 报告形式呈现候选方案

将一个独立的 HTML 文件写入操作系统临时目录，这样就不会有任何内容被上传到代码仓库。临时目录从 `$TMPDIR` 解析，如果解析失败则使用 `/tmp`（Windows 系统下为 `%TEMP%`），并将文件写入 `<tmpdir>/architecture-review-<timestamp>.html`，以便每次运行都生成一个新文件。用户可以通过 `xdg-open <path>`（Linux 系统）、`open <path>`（macOS 系统）或 `start <path>`（Windows 系统）打开该文件，并告知用户绝对路径。

该报告使用 **Tailwind（通过 CDN）** 进行布局和样式设置，并使用 **Mermaid（通过 CDN）** 生成图表，其中图表/流程图/序列图能够可靠地传达结构信息。将 Mermaid 与手工绘制的 CSS/SVG 视觉元素结合使用——当关系呈图表形式时（例如调用图、依赖关系、序列），使用 Mermaid；当需要更具编辑性的效果时（例如批量图表、横截面图、折叠动画），则使用手工绘制的 div/SVG。每个候选对象都会获得一个**前后对比**效果图。注重视觉呈现。

对于每个候选方案，请生成一张包含以下内容的卡片：

- **文件** — 涉及哪些文件/模块

- **问题** — 当前架构造成摩擦的原因

- **解决方案** — 用简洁的英语描述将要进行的更改

- **优势** — 从局部性和可扩展性的角度进行解释，并说明如何改进测试

- **前后对比图** — 并排绘制的自定义图表，展示架构的浅层化和深化

- **推荐强度** — “强烈推荐”、“值得探索”或“推测性”之一，以徽章的形式呈现

报告末尾添加“最佳推荐”部分：说明您会首先着手哪个候选方案以及原因。

**领域描述请使用 CONTEXT.md 中的词汇表，架构描述请使用 `/codebase-design` 中的词汇表。** 如果 `CONTEXT.md` 定义了“订单”，请描述“订单接收模块”，而不是“FooBarHandler”或“订单服务”。

**ADR 冲突**：如果候选方案与现有 ADR 相冲突，则仅当冲突足够严重，需要重新审视 ADR 时才将其提出。在卡片中清晰标记（例如，警告标注：“与 ADR-0007 相冲突——但值得重新审视，因为……”）。不要列出 ADR 禁止的所有理论上的重构。

请参阅 [HTML-REPORT.md](HTML-REPORT.md) 获取完整的 HTML 框架、图表模式和样式指南。

暂时不要提出接口方案。文件编写完成后，询问用户：“您想探索哪些方案？”

### 3. 筛选循环

用户选择候选方案后，运行 `/grilling` 技能，与他们一起遍历决策树——约束、依赖关系等。
