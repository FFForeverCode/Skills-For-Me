---
名称：生成 TRD 技术方案文档

描述：基于用户提供的 PRD 与当前代码库，产出可评审、可落地、可追踪改造点的 TRD（Technical Requirement/Design Document）。方案必须以“真实代码现状 + 业务需求差异”为核心，不得脱离代码库空想设计。
---

## 1. 适用场景

当用户希望：
- 根据 PRD 设计技术方案
- 评估需求对现有系统影响
- 明确改造范围、接口、数据与发布策略
- 输出可直接用于评审的 TRD

## 2. 核心原则

- **模板优先**：用户给了模板就严格按模板输出，不擅自改章节与顺序。
- **事实优先**：与现状相关的结论必须来自代码库或用户资料。
- **Gap 驱动**：先做“需求 vs 现状”差异分析，再做方案设计。
- **可落地优先**：要明确改哪些模块/类/方法，不只讲概念。
- **不编造**：不虚构代码、指标、依赖、链路；未知项标记“待确认”。

## 3. 输入要求（按优先级）

### 3.1 PRD（必需）

至少提取：
- 业务背景与目标
- 功能与业务规则
- 核心流程与角色
- 边界/异常场景
- 数据与非功能要求（性能、兼容性、安全性）

若 PRD 信息冲突或缺失：明确列出问题清单，不自行补完。

### 3.2 代码库（强依赖）

围绕需求做定向定位，不做无目的全量遍历：
- 模块与目录结构
- API/Controller → Service → Repository/DAO
- Entity/DTO/VO、SQL/表结构、缓存、消息、RPC/HTTP 依赖
- 配置、定时/异步任务、事务边界、异常处理策略

### 3.3 TRD 模板（可选）

若用户提供模板，必须遵循：
- 标题层级
- 字段名与表格结构
- 文档顺序与格式规范

无法填充处写：`待补充` 或 `当前代码库未发现相关实现，需进一步确认`。

## 4. 标准工作流

### Step 1：需求理解（先不写方案）

输出“需求理解摘要”，回答：
- 为什么做、做什么、谁使用
- 新增/变更了哪些能力
- 核心规则与边界条件

### Step 2：代码定位与现状梳理

按链路定位相关实现：
`API → Controller → Service → Repository/DAO → DB/Redis/MQ/RPC`

同步识别：
- 当前业务流程与状态流转
- 数据流与调用链
- 缓存/消息/事务/异常处理机制

### Step 3：建立现状模型

至少覆盖四个视角：
- **架构视角**：实际组件与调用关系
- **流程视角**：请求进入到结果返回完整路径
- **数据视角**：实体、表、索引、关系、生命周期
- **依赖视角**：上下游、第三方、外部风险点

### Step 4：Gap 分析（关键步骤）

使用表格描述：
`需求项 | 当前实现 | 差异 | 改造方向 | 风险`

只有 Gap 明确后，才进入技术设计。

### Step 5：技术方案设计

按需覆盖以下模块（只写与需求相关内容）：
- 架构与模块改造
- 核心业务流程（文字或 Mermaid）
- 数据库设计（字段/索引/迁移/兼容）
- API 设计（协议、入参、出参、错误码、幂等、权限）
- 缓存设计（Key、TTL、一致性、热 Key、失效策略）
- MQ 设计（Topic、消费语义、重试、死信、幂等）
- 并发与一致性（锁、事务、CAS、最终一致性策略）

禁止“炫技式”引入 Redis/MQ/分布式锁；必须说明引入动机与收益。

### Step 6：异常、稳定性与发布设计

必须包含：
- 异常与边界场景处理闭环：`触发 → 检测 → 处理 → 重试/补偿 → 收敛`
- 性能与容量评估（无数据时明确标注待确认项）
- 兼容与发布策略（灰度、回滚、不可逆操作防护）

### Step 7：代码改造清单

对关键改造点给到可执行粒度：
`模块/文件路径 → 类/方法 → 修改点`

优先引用真实路径；禁止虚构文件和方法。

### Step 8：测试与验收设计

最少包含：
- 功能：正常、异常、边界
- 并发：重复请求、竞态、幂等
- 数据：一致性、迁移、兼容
- 稳定性：依赖故障注入（DB/Redis/MQ/RPC）

## 5. TRD 输出结构（默认模板）

当用户未提供模板时，使用以下结构：

1. 背景与目标
2. 需求范围与非范围
3. 需求理解与关键规则
4. 系统现状分析
5. Gap 分析
6. 技术方案总览
7. 详细设计（流程/数据/API/缓存/MQ/一致性）
8. 异常与边界场景
9. 性能与稳定性评估
10. 发布、灰度与回滚方案
11. 代码改造清单
12. 测试与验收方案
13. 风险与待确认项

## 6. 质量门禁（生成前自检）

发布 TRD 前逐项检查：
- 是否所有关键结论可追溯到 PRD 或代码
- 是否完成了明确的 Gap 表
- 是否给出了可执行改造清单（文件/类/方法级）
- 是否覆盖异常、兼容、回滚、性能风险
- 是否存在“假设性指标/假设性代码结构”
- 所有未知项是否明确标注为 `待确认`

## 7. 输出风格要求

- 结论先行，先摘要再细节。
- 使用结构化标题、表格、清单，避免大段空泛描述。
- 术语与命名保持与项目一致。
- 内容紧贴当前需求，避免无关章节堆砌。

---

目标：最终 TRD 必须让研发、测试、架构师和产品能直接评审并进入实施，而非停留在概念层。
